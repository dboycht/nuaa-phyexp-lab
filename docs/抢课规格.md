# 抢课规格（自动填充空闲时间段）

> 用途：把"用户选空闲时段 → 系统自动尽量多选上实验"这条需求**写成可执行的规则**，
> 先给用户审阅确认，再照此实现（避免按想象写代码）。
> 状态：**规则已由用户逐项确认（2026-10-07）**，本文即 1.0.3 的实现依据与验收判据。
> 相关：`docs/选课与退课.md`（写接口与 `status:false` 坑）、`DEVELOPMENT.md` §6.2。

---

## 一、一句话目标

> **用户给出"自己空闲的具体日期 + 节次"，系统在选课窗口开启后自动筛选出落在这些时段内、且有余量的实验场次，
> 尽可能多地提交选课，直到每个空闲时段都占上一个实验（或已无可用余量 / 达到用户设定的上限）。**

---

## 二、系统的真实时间结构（**实测**，2026-10-07）

课程 id=71 当天 7 天、55 个场次，节次固定为 **5 个**：

| 节次 | 时间 |
| --- | --- |
| 上午1、2节 | 08:30–10:15 |
| 上午3、4节 | 10:30–12:15 |
| 下午5、6节 | 14:00–15:45 |
| 下午7、8节 | 16:00–17:45 |
| 晚上9，10节 | 18:45–20:30 |

- 每个"场次"= **一个日期 × 一个节次 × 一个实验项目**，有独立容量（`max_student_number`）与已选数；
- 某一天**只开部分节次**（如 10-12 只有下午7、8节与晚上9、10节）⇒ 筛候选时必须按**实际存在的场次**判断，
  不能假定"勾了节次就一定有课"。

---

## 三、核心规则（R1–R8）

| 编号 | 规则 | 说明 |
| --- | --- | --- |
| **R1** | **空闲时段 = 具体日期 + 节次** | 用户按日历勾选（可跨天、可只勾某天的某节） |
| **R2** | **同一「日期+节次」最多占 1 个实验** | 避免同一时段撞车；这是"不冲突"的硬约束 |
| **R3** | **候选 = 落在空闲时段内 且 `余量 > 0` 的场次** | 余量 = `max_student_number − current_student_number`；前端自身也用同一判据 |
| **R4** | **优先级 = 余量多的先抢** | "成功概率高"优先；余量相同时按（日期升序 → 节次顺序 → 实验编号）稳定排序 |
| **R5** | **不设总量上限** | 有空闲时段就填；若用户想限制，另设可选上限（默认关闭） |
| **R6** | **抢完必须回读核实** | 每条选课提交后回读 `rest/user2projects` 确认 `schedule_id` 已 `elected`；**不拿 HTTP 200 当成功**（见 `docs/选课与退课.md`） |
| **R7** | **失败即降级到下一个候选** | 某个场次失败（已满/限流/拒绝）→ 标记该场次不可用，继续尝试下一个候选；**同一时段的其他实验仍可继续尝试** |
| **R8** | **不撞重复实验** | 已选过某实验项目（或本轮已占该实验）时跳过，避免重复选同一实验 |

**停止条件**（满足任一即停）：

1. 所有空闲时段都已占上一个实验；
2. 没有"落在空闲时段内且有余量、且可尝试"的候选了；
3. 达到用户设定的可选上限（默认不设）；
4. 用户手动中断；
5. 达到最大轮次/超时（防跑飞，默认给个上限并在日志里说明）。

## 四、配置（草案；真实配置不进仓库）

**落点**（用户已确认）：真实配置 `%LOCALAPPDATA%\PhyExpLab\config.json`；仓库内放 `config.example.json` 示例 + 文档。
缺配置时**自动生成默认配置并明确提示**（不静默用内置默认值）。

```jsonc
{
  "course_id": 71,                    // 课程 id（默认取"我的第一门课"）
  "free_slots": [                     // R1：按具体日期+节次
    { "date": "2026-10-14", "period": "下午5、6节" },
    { "date": "2026-10-15", "period": "晚上9，10节" }
  ],
  "priority": "remaining_desc",       // R4：余量多的先抢（默认）
  "max_total": 0,                     // R5：0 = 不设上限
  "dry_run": true,                    // 安全默认：默认演练，显式关闭才真提交
  "submit": {                         // 沿用 grabber.GrabConfig（已按实测校准）
    "prewarm": true,
    "pre_fire_offset_ms": 50,
    "min_submit_interval_ms": 800,
    "max_attempts_per_target": 3
  }
}
```

## 五、运行流程（伪代码）

```
1. 读配置 → 校验（日期格式 / 节次名是否在系统 5 个节次里 / 是否与已选记录冲突）
2. 登录态检查（token 未过期，否则提示先 login）
3. 拉取：开放学期 → 我的课程 → 课程下全部场次（含余量）
4. 计算已占用的「日期+节次」集合（来自"我的选课记录"）        ← R2 的前置
5. 生成候选：落在空闲时段内 ∧ 余量>0 ∧ 未被占用 ∧ 未选过该实验  ← R2/R3/R8
6. 按 R4 排序
7. 逐个尝试（保持 min_submit_interval_ms 间隔）：
     - 提交选课 → 回读核实（R6）
     - 成功 ⇒ 标记该「日期+节次」已占，记录日志
     - 失败 ⇒ 标记该场次不可用，继续下一个（R7）
8. 打印总结：成功清单 / 失败及原因 / 未覆盖的空闲时段（如实说明，不粉饰）
```

## 六、验收判据（可执行）

| 编号 | 判据 |
| --- | --- |
| A1 | 给定若干空闲时段，**每个时段最多出现 1 条**成功的选课记录（R2） |
| A2 | 成功清单里的每条，都能在 `rest/user2projects` 回读到对应 `schedule_id` 且 `status=elected`（R6） |
| A3 | 落选/失败的场次在日志里**有明确原因**（已满/限流/拒绝/未知），不得静默跳过（R7） |
| A4 | 默认 `dry_run=true`：不加显式开关**绝不发写请求**（沿用现有安全设计） |
| A5 | 完成输出必须列出"**没能覆盖的空闲时段**"及原因（没有就写"全覆盖"） |
| A6 | 演练模式下，候选清单与排序结果与实际提交顺序**完全一致**（保证演练可信） |
| A7 | 已选过的实验项目**不再出现在候选里**（D6）；判定依据是"我的选课记录"里的 `project_id` |
| A8 | `--at` 到点自动开抢：等待期间 token 过期 ⇒ **发出提醒通知且不静默提交**（D7 / token 风险） |
| A9 | 通知失败（异常/不支持/超时）时，**抢课结果与日志不受影响**（通知失败不致命） |
| A10 | 抢完后（`--real`）必须依次：**列出本轮抢到的每条**（含 `user2project_id`）→ 允许按序号选择退课 → **二次确认**（默认 N）→ 执行并**回读核实**；用户直接回车 = **全部保留** |
| A11 | 退课选择**只认数字**（`1,3` / `1-2` / 空回车；非法输入必须报错重问，**不许猜**）；非交互终端必须**跳过提问**并提示 `cancel --id`，不得挂住 |
| A12 | 日历/两周边界只影响"显示与选择范围"，**不影响已确认的规则**（每个空闲时段最多 1 个、余量多者先抢等） |

## 七、已确认的决策（**2026-10-07 用户逐项确认**）

| 编号 | 问题 | 决策 |
| --- | --- | --- |
| D1 | 空闲时段怎么表达 | **按具体日期 + 节次**（日历形式，最灵活） |
| D2 | 同一时段冲突 | **同一「日期+节次」最多占 1 个实验**（硬约束） |
| D3 | 候选优先级 | **余量多的先抢**（成功概率高优先） |
| D4 | 余量相同时 | **日期早的优先**（再并列则按节次顺序 → 实验编号，保证排序稳定） |
| D5 | 总量上限 | **不设上限**（有空闲就填；可选 `max_total` 默认 0 = 关闭） |
| D6 | 同一实验能否重复选 | **不允许** —— 已选过的实验项目**跳过**（R8） |
| D7 | 触发方式 | **要定时自动开抢 + 桌面通知**（用户明确要求） |
| D8 | 配置落点 | **运行时目录** `%LOCALAPPDATA%\PhyExpLab\config.json` + 仓库内 `config.example.json` 示例 |
| D9 | GUI | **本轮不做**，先只做 CLI + 配置 |

### 7.1 D7 的落地设计（定时自动开抢 + 桌面通知）

**目标**：到点无人值守也能抢，并在结束时**主动告诉用户结果**（不用一直盯终端）。

| 组件 | 做法 | 理由 |
| --- | --- | --- |
| **到点自动执行** | 独立进程 + **定时启动**（沿用 `watch-bg` 已验证的"脱离会话独立进程"套路）：`抢课 --at <目标时刻>` 进入等待，到点自动开抢 | 实测教训：会话级后台任务跑不长（`ERROR.md` E10），长等待必须独立进程 + 文件日志 + PID 落盘 |
| **桌面通知** | 结束时发 Windows 通知（气泡/Toast）；失败或"有空闲时段没抢到"**也发**，并在正文里写明原因 | 通知的价值在"人不在电脑前也能知道结果"；只在成功时通知会漏掉最需要知道的失败 |
| **token 风险（重要）** | JWT 实测 **2 小时**过期。若目标时刻距离启动时超过 ~100 分钟：**在等待期间定时检查 token**，过期即发通知提醒重新登录，并**不静默继续** | 否则会"到点了，但发出去的请求全是 401"，而用户以为在抢 |
| **通知失败不致命** | 通知模块异常只记日志，**不影响抢课结果** | 通知是附属能力，不能反过来把主流程搞挂 |
| **可关闭** | 配置项 `notify: true/false`，默认开启；也支持 `--no-notify` | 有人不想被弹窗打扰 |

> ⚠️ **通知的边界（不夸大）**：它只保证"本机发过一条通知"；
> **不保证用户一定看到**（勿扰模式/全屏程序可能吞掉）。因此**日志与终端输出仍是主记录**，
> 通知只是"多一条通道"，验收时以 `logs\` 下的记录为准。

## 七·五、完整操作流程（**用户 2026-10-07 口述**，实现须照此）

```
① 设定空闲时间段【日历上点击即可】
     范围：一般要覆盖 **两周**（本周 + 下周）
     原因：实验在周一上午 10:00 开抢，两周的场次通常同时放出来
② 设定抢课时间段（到点开抢的时刻）
③ 登录后自动开始等待
④ 到点：自动抢（按 §三 的规则尽量多选）
⑤ 抢到后**弹出窗口汇报**（抢到了什么 / 没抢到什么，都要说）
⑥ 用户可以选择**退课**（当场挑要退的，二次确认）
```

## 八、术语与边界

- **场次（slot / lesson）**：一个"日期 × 节次 × 实验项目"的可预约单位，有独立余量。
- **节次**：系统固定 5 个（见 §二），**节次名必须与系统完全一致**（含"晚上9，10节"里的中文逗号）——
  配置里写错名字要**立刻报错并列出合法取值**，不能静默当成"没有候选"。
- **本轮不做**：验证码绕行、多账号、并发轰炸。
- ⚠️ **GUI 状态变更（2026-10-07）**：原定"本轮不做 GUI"，但用户随后明确了完整操作流程
  （§七·五），其中"**日历上点击选空闲时段**"与"**弹出窗口汇报**"必须由 GUI 承载 ⇒
  **GUI 从"不做"改为"待做"**（见 §七·五 表格）。CLI 已具备等价功能，GUI 是交互层的补充。
- **合规**：保持低频（提交间隔 ≥800ms，沿用已校准参数）；不绕过任何风控机制。
