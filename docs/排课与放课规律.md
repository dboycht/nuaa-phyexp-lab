## 三、采样方法（纪律优先：低频、只读、可中断）

1. **只读**：研究阶段**只发 GET/查询**，不调用任何选课/退课写接口。
2. **低频**：默认最小间隔 `>= 3s`（`monitor.MonitorConfig.min_interval_seconds`），命中限速立即指数退避；
   研究期建议 **60–300s** 一轮，仅在「预计放闸时间窗（如整点前后 5 分钟）」临时收紧到 3–10s。
3. **落盘格式**（本地，不进仓库）：每轮一条 JSONL 记录
   ```json
   {"t":"2026-09-21T18:56:47+08:00","slot_id":"...","taken":12,"capacity":20,"status":"elected","http_ms":312}
   ```
4. **可中断**：长跑监控随时 Ctrl+C，已采数据必须已落盘（不得只在内存里攒）。
5. **样本记账**：每轮采样记录轮次与失败原因（超时/限速/登录过期），方便判断数据是否可信 —— **失败轮次不得计入规律统计**。

## 四、分析维度

- **时间轴**：余量随时间的变化曲线（按场次）；标记出「放闸点」与「满员点」。
- **周期维度**：按星期几 / 节次统计放出量（若系统是分批放课）。
- **热度**：按项目统计「满员所需时间」与「退课率」。
- **竞争**：热门项目的余量「存活时间」（从出现空位到再次满员）。
- **限速画像**：记录每次被判限速的请求间隔，得出安全间隔下界。

### 5.2 尚不能下的结论（**明确不要**当成规律）

| 问题 | 为什么现在不能下结论 |
| --- | --- |
| Q1 放闸时刻规律 | 本批采样只有 78 分钟、且全在**晚上**，没有覆盖放课时段；需要跨天、覆盖整点前后的长采样 |
| Q3 退课高峰时段 | 同样受"只在晚上采样"限制 —— C4 只能说明"这批样本里发生在晚上"，不能反推"退课集中在晚上" |
| Q5 空位存活时间 | 5 个空位在样本期内**都没被抢走**，只给出存活时间**下界**，没有闭合样本 |
| Q6 竞争速度 | 被抢事件为 0，无法度量"一个空位能活多久" |

### 5.3 采样纪律与已知限制（实测踩到，写在这里免得后人重复）

1. **token 只有 2 小时**（实测 `exp`）：连续采样会被迫中断，必须周期性重新 `python run.py login`。
   因此**长时研究要跨多次会话**；好在 `analyze` 会把多个样本文件合并分析。
2. **长跑任务不要把进度只写在 stdout 上**：实测两次后台采样任务都在"下一次 print"时静默消失
   （裸 exit 1、无 traceback）。现已改为 `monitor.FileLogger`：**进度先落盘、再尽力 print**，
   print 失败就永久关掉 stdout（见 `ERROR.md` E10）。
3. **间隔选择**：研究期 60–300 秒足够；只有在"确认放闸时刻"或"追捡漏"时才临时收紧到 3–10 秒。
4. **失败轮次不计入样本**：某个项目查询失败只记录，不把该轮写成"余量为 0"。
